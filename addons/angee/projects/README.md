# Projects

- [Standard project and task declarations](web/src/index.tsx) are shared by routed pages and collection presets. Consumers select groups, tabs, verbs and context through their exported options; a `ResourceList` mounts their List and Form elements directly so the declaration parser can see them.
- `useProjectListDeclaration(options)` composes the standard project list with caller-selected views, groups and other list options; `projectListDeclaration` is its default call. Gantt starts without a URL group. Verb labels come from the `projects` messages (`project.action.pause`, `.resume`, `.complete`, `.drop`, and `task.action.complete`, `.drop`, `.reopen`, `.promote`); consumers override those message keys through vocabulary rather than a parallel label option.
- The [form header](../../../packages/ui/src/views/form/form-view-body.tsx) renders a `status` field once. Project phase uses the [phase widget](web/src/project-phase.tsx); Task visibility uses the [shared visibility widget](../../../packages/ui/src/widgets/visibility.tsx) beside the title. Task publication choices and the locked verb share [`visibility_blockers`](models.py). Task hand verbs and the `task_actions` projection share [`action_blockers`](models.py); the standard form offers Complete, Drop and Reopen only where `offersTaskAction` reads them admitted.
- The phase widget fills the record width from milestone rows. `selectable_milestones` alone enables phase choices, which confirm before the project verb runs. Milestone `write` permission enables dates at each step through the milestone resource update; the project-owned `on_path` and `status_changed_at` projections place paused, completed and dropped state in the bar instead of a second title badge. Lifecycle verbs stay in the form header.
- The [project Gantt](web/src/project-declarations.tsx) places milestones on project lanes and scopes queries to visible projects; the record Timeline includes task due markers. [Resource links](../../../packages/ui/src/runtime/runtime.ts) use owner-declared route discriminators.
- [`Project.objects.setup_from_task`](models.py) owns atomic promotion and setup. Its receipt guards replay; typed [GraphQL input](schema.py) and cooperative `apply_setup` hooks compose milestone, binding and round setup. Partial projects adopt uniquely named existing milestones; failures leave no receipt or partial acts.
- [Project and Task projections](schema.py) report setup state and overdue phase counts. A phase-specific queue names its milestone when requesting the count.
- A record task is a task whose `subject` is a record's chatter attachment, typed by a resource-declared [`ActivityType`](models.py) (`ActivityType.DEFAULT_KEY` when none is named). [`Task.objects.schedule`, `log` and `for_record`](models.py) write and read them under the actor; the generic verbs complete and drop them, open only, and a completion posts on the record's chatter (subtype `activity_done`) through [`Task.post_completion`](models.py). [permissions.zed](permissions.zed) derives their access from the record alone (the record's readers read, its writers write, share, complete and delete; a record task's own grants do not count): a record type takes them once its owner declares `record_read` and `record_write` for it on `messaging/thread_attachment` in its `permissions.extends.zed`, as projects does for tasks and projects (a task lends `read_as_subject`/`write_as_subject`, its direct holders, which work extends with its queue, so task access never recurses, and a withheld task withholds them through `record_withheld`) and [the notes example](../../../examples/addons/example/notes/permissions.extends.zed) does for notes. The `projects.tasks` tab on `record#aside` lists, schedules, logs, completes and cancels them.
