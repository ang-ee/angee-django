# Projects

- [Standard project and task declarations](web/src/index.tsx) are shared by routed pages and collection presets. Consumers select groups, tabs, verbs and context through their exported options; a `ResourceList` mounts their List and Form elements directly so the declaration parser can see them.
- `useProjectListDeclaration(options)` composes the standard project list with caller-selected views, groups and other list options; `projectListDeclaration` is its default call. Gantt starts without a URL group. Verb labels come from the `projects` messages (`project.action.pause`, `.resume`, `.complete`, `.drop`, and `task.action.complete`, `.drop`, `.reopen`, `.promote`); consumers override those message keys through vocabulary rather than a parallel label option.
- The [form header](../../../packages/ui/src/views/form/form-view-body.tsx) renders a `status` field once. Project phase uses the [phase widget](web/src/project-phase.tsx); Task visibility uses the [shared visibility widget](../../../packages/ui/src/widgets/visibility.tsx) beside the title. Task publication choices and the locked verb share [`visibility_blockers`](models.py). Task hand verbs and the `task_actions` projection share [`action_blockers`](models.py); the standard form offers Complete, Drop and Reopen only where `offersTaskAction` reads them admitted.
- The phase widget fills the record width from milestone rows. `selectable_milestones` alone enables phase choices, which confirm before the project verb runs. Milestone `write` permission enables dates at each step through the milestone resource update; the project-owned `on_path` and `status_changed_at` projections place paused, completed and dropped state in the bar instead of a second title badge. Lifecycle verbs stay in the form header.
- The [project Gantt](web/src/project-declarations.tsx) places milestones on project lanes and scopes queries to visible projects; the record Timeline includes task due markers. [Resource links](../../../packages/ui/src/runtime/runtime.ts) use owner-declared route discriminators.
- [`Project.objects.setup_from_task`](models.py) owns atomic promotion and setup. Its receipt guards replay; typed [GraphQL input](schema.py) and cooperative `apply_setup` hooks compose milestone, binding and round setup. Partial projects adopt uniquely named existing milestones; failures leave no receipt or partial acts.
- A project with `is_template` is a template: [`Project.objects.create_from_template(template, idempotency_key=, values=, task=, anchors=, role_mapping=)`](models.py) copies it atomically, idempotently per actor and key, under template read and project create. `Project.copy_template` carries the project's tags and `template_copy_values`, its phases in order through `Milestone.setup_template_values` (the setup path's one milestone input, which contributors extend, as work does with `active_stage`), its open tasks and subtasks the actor reads with their tags and the relations between them, and every due rule. Dates, lifecycle, statements, grants, participants, bindings, links and files never copy. A template task's `assignee_role` (a key the consumer names) takes the person `role_mapping` names for it; an unmapped role stays a role with no assignee. With `task=`, the copy is the task's promoted project (`from_task`), titled, described and led from the task. A template carries no source statements (`validate_template`, which contributors extend). Ordinary lists, boards, My Work, waiting-on attention and overdue phases leave templates out (`is_template`, the task resource's `in_template` filter); the Templates page lists them, and a template's form offers Create project.
- Tasks and milestones compose [`RuleDatedMixin`](models.py): `due_rule` (an [`angee.scheduling`](../scheduling/README.md) `DueRule`; `NULL` means the date is set by hand) resolves into the row's own date (`Task.due_date` and the aware `Task.due_at`; `Milestone.target_date`) and `due_basis`. Anchors come from the project: `created` (its creation instant) and the named `due_anchors` `Project.set_due_anchor` records, which re-resolves the open rows that follow rules; a template supplies none, so its rules stay pending. A task about no project counts from its own creation, and every row supplies `set`, its own date. A row follows its rule while its date equals the basis point; a hand or stated date that differs wins, the basis keeps the rule's value, and `reset_due_to_rule` (GraphQL `reset_task_due_to_rule`, `reset_milestone_due_to_rule`) hands the date back. `due_status` is read through the rule while it is followed, else through a one-term `set` rule. Completing a task whose rule repeats creates its next task once (`create_repetition`, from `post_completion`; `repeated_from` is one-to-one), due at `DueRule.resolve_next` from the completed task.
- [Project and Task projections](schema.py) report setup state and overdue phase counts. A phase-specific queue names its milestone when requesting the count.
- A record task points directly at its subject through `RecordRefMixin`. The target type's declared `subject_read`, `subject_write`, and optional `subject_withheld` arms on `projects/task` own its access. The Tasks aside uses the generated `recordEdges` capability; chatter is optional. `schedule` and `log` use the native generic target and actor gates; completion posts only when the subject composes chatter.
- Task ancestry composes `HierarchyMixin`; `parent`/`children` and the maintained path are one tree. Lifecycle (`open`, `done`, `dropped`) is separate from removal (`TrashMixin`) and duplicate identity (`merged_into`). Merging reuses the core coordinator and appends children using their native fractional rank owner.
- A system of record (an integration whose `integrate.RecordLink` names the row) states projects, milestones and tasks through their [`StatementRecords`](models.py) aspects: `identity`, `lifecycle`, `schedule`, `assignment` on a project; `identity`, `lifecycle` (the receipt), `schedule` on a milestone; `identity`, `lifecycle`, `schedule`, `priority`, `assignment`, `structure` (project, milestone, parent) on a task. Every aspect lists PERSON before SYSTEM_OF_RECORD, so an authoritative stream outranks a person's normal stance and a plain one does not; a person's confirm or dismiss stays on top. A stated lifecycle applies through its owner: `_set_status` on a project, `mark_reached` on a milestone (a stamped receipt is historical, so only stances stating it compete), and the `complete`/`drop`/`reopen` verbs on a task, so a queued task enters the stage that projects the stated status; the verbs' blockers refuse a statement they cannot apply. Announcements and completion posts fire only for a state that survives the save. `StatedRecordMixin` admits a source through `write_statements` alone (permissions.zed), never through `read` or `write`, so milestones, tasks and bound resources inheriting a project's access lend a source nothing. A row records a person's stance only once a source states it; until then it is an ordinary row. Statements protect a stated row and every row they name (its project, milestone, parent task, lead or assignee) from deletion: `delete_blocker` reports it and the statement tables' protected keys enforce it. Consumer donors contribute their own aspects to the same tables.
- Project history includes its owned milestones. Task, milestone, relation, participant, binding and link writes use the shared changeset history; no chatter field-tracking store remains.
